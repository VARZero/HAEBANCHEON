# HAEBANCHEON — BoAYO components-v6

Dashboard·Telemetry·SDK Pulse와 BoAYO 공통 창 조작부를 사전 제작 에셋으로 구동하는 SD 이미지다. 기존 `updates/boayo-tiles-v5`는 비교 기준으로 보존했다. 대상은 L1I/D 각각 16KiB·2Way, DMA 3개인 PZ-A7200T-KFB 구성이다.

## 역할과 실행 경로

- 닫기, 크기 조절, 위치 이동 버튼은 **BoAYO 공통 컴포넌트**다. 각 앱의 내용과 별도로 생성·배치·입력 처리한다. 공통 `caption_sync`와 창 관리 동작을 유지한다.
- 앱은 자신의 내용과 상태를 제공한다. Dashboard의 숫자, Telemetry의 막대, SDK Pulse의 숫자와 막대는 미리 만든 조각을 선택해 조합한다.
- PC에서 원래 그리기 코드를 이용해 고정 배경·글자·막대·버튼을 장치용 비압축 `0x00RRGGBB` 데이터로 만든다. 보드 CPU는 주소·배치·상태·요청을 관리한다.
- 보드에서는 읽기 전용 에셋을 매핑하고 DMA로 기본 이미지와 작은 변경 조각을 순서대로 전송한다. 일반 경로에서 앱 전체 RGB 배열로 변환하거나 CPU로 복사·비교하지 않는다. 현재 변경 프레임에서도 기본 이미지의 DMA 업로드는 수행한다.
- 투영코어는 준비된 기하·마스크와 텍스처로 타일을 만들고, 출력코어는 완료된 장면을 전환한다. 빈 타일은 `0xffffffff` 디렉터리 항목으로 표현한다. 장면 전체 픽셀 영역을 0으로 채우지 않는다. 실제 경계 합성에 필요한 타일만 초기화한다.

메모리 소유권, DMA 완료 확인, 실패 시 게시 중단은 유지한다. 반복적인 전체 픽셀 검증은 정상 실행 경로에 넣지 않았다. 에셋의 SHA·CRC·키·크기 전수 검사는 이미지 제작 PC에서 수행한다.

## 사전 제작 범위와 기능 유지

`asset_catalog.json`이 앱과 기본 배치 목록을 정의한다. 앱별 기본 배치 세 가지(방위각 0, -12, +12도)에 실제 공통 버튼까지 포함한 계획을 만든다. 중복 제거 후 37개 계획이며, 모든 계획을 SD 파일시스템과 초기 파일시스템에 배치한다. 기존처럼 런처 계획 하나만 배치하지 않는다.

공통 버튼 높이는 40·80·100을 준비했다. 이전 카탈로그에는 실제 이동 버튼의 높이 100이 빠져 CPU 그리기로 돌아가는 경우가 있었다.

에셋은 총 689개다. 앱 기본 이미지, 숫자 글리프, 막대 조각, 공통 창 버튼과 기존 런처·보관 창을 포함한다. 앱의 프레임은 기존 BoAYO 공통 프레임 생성기를 사용한다. 임의의 새 버튼 구현을 각 앱에 복제하지 않는다.

자유로운 이동·크기 변경·각도 변경은 유지한다. 사전 제작하지 않은 기하, 비표준 이미지 크기·상태는 기존 계산 경로를 사용한다. Dashboard의 0이 아닌 yaw/pitch 텍스트, SDK Pulse의 비표준 크기 표시는 기존 그리기 경로로 돌아간다. 따라서 모든 이동·크기 변경이 CPU 계산 없이 처리되는 것은 아니다.

## 이미지와 비트스트림

- 새 이미지: `HAEBANCHEON-KFB-BoAYO-components-v6.img`
- 기존 비트스트림: `HAEBANCHEON-KFB-L1-16K-DMA3-v1.bit`
- 이미지 표시: `/etc/oryukdo-image`에 `HAEBANCHEON-BoAYO-components-v6`
- Linux: `6.12.0-haebancheon-components6`
- BusyBox, OpenSBI, L1/DMA3용 Linux 드라이버와 coherent DT 구성은 보존했다.
- RTL·MIG·HDMI IP는 변경하지 않았다. 이번 작업으로 합성·배선을 다시 수행하지 않았다.

기존 보드 구성을 위한 드라이버가 포함된 `/var/tmp/haebancheon-l1-16k-dma3/release`를 빌드 기준으로 사용한다. 이 폴더 안의 구버전 `software/bosio/driver` 사본을 커널에 덮어쓰지 않는다. `build_l1_image.sh`가 사용하는 실제 드라이버와 DT는 최종 L1/DMA3 구성으로 검증한다.

앱·공통 버튼의 필수 에셋과 계획은 약 32MiB의 초기 파일시스템 공간을 사용한다. 전체 에셋도 `/data` ext4에 들어 있다. 이는 부팅 때 읽을 데이터가 증가하는 선택이다. 데몬 실행 이후 CPU 그리기 감소와 Linux 콜드 부팅 시간은 별도로 평가해야 한다.

## 검증 범위

실행 결과는 `evidence`와 전달 폴더의 `reports`를 참조한다.

- 보존한 v5 CPU 그리기 결과와 123개 앱 상태의 픽셀을 정확히 비교한다.
- 여러 창의 겹침, 상태 갱신, 포커스, 닫기와 뒤쪽 창 복원, 카메라 변경을 13개 장면에서 비교한다.
- ASan/UBSan과 기존 9개 회귀 그룹을 실행한다.
- 실제 RV32 Linux 이미지의 BusyBox, DDR 상위 메모리 검사, 세 앱 출력 완료와 WASD·클릭을 QEMU에서 확인한다. BOSIO는 명시적인 Mock Backend다.
- RV32의 10개 다중 창 장면을 PC 기준 장면과 비교한다.
- 실제 출력 캐시 RTL에 3개 완성 장면을 넣고 37,980개 샘플 픽셀을 확인한다.
- 실제 SD 부트로더·SD4·DMA RTL에 새 이미지 내용을 넣어 부팅 페이로드의 DDR 전송과 CRC, 런타임 읽기·쓰기를 확인한다. DDR와 SD 카드 외부는 모델이다.
- 실제 이미지의 커널·초기 파일시스템·실행 파일·에셋·계획·ext4 데이터가 빌드 결과와 같은지 검사한다.

이 검증은 전체 CPU RTL에서 Linux와 BoAYO를 부팅한 결과나 새 이미지의 실보드 HDMI 확인을 뜻하지 않는다. 실제 첫 화면 시간과 창 전환 시간은 새 SD를 기록한 뒤 측정해야 한다.

## 재현

WSL Ubuntu에서 실행한다. 기존 Linux 기준 빌드와 RV32 툴체인이 필요하다.

```sh
bash build.sh /var/tmp/haebancheon-components-v6
bash validate.sh /var/tmp/haebancheon-components-v6
```

다른 기준 바이너리는 `CPU_BASELINE`, Linux 기준 빌드는 `BASE_BUILD`로 지정한다. 비교 기준 v5 바이너리를 새 버전으로 덮어쓰지 않는다.

## 에셋을 추가하는 방법

1. BoAYO 공통 조작부인지 앱의 내용인지 먼저 구분한다. 공통 버튼은 `caption_image`와 공통 입력 처리에 추가한다.
2. `tests/make_assets.py`에 키·형상·상태를 정의한다. 기존 렌더러가 PC에서 실제 픽셀을 생성한다.
3. 앱의 작은 가변 요소는 `app_recipe`에 주소와 사각형 목록으로 연결한다. DMA 전달의 원본 수명과 완료 순서를 지킨다.
4. 필요한 기본 배치를 `asset_catalog.json`에 추가하고 계획을 다시 생성한다. 모든 가능한 위치를 임의로 양자화하지 않는다.
5. 픽셀·겹침·입력 회귀 검사, 이미지 무결성 검사를 통과한 결과를 이미지에 넣는다.

에셋 키나 알고리즘을 바꿨다면 기존 생성 폴더를 덮어쓰지 말고 새 작업 폴더를 사용한다. 생성기는 같은 이름의 다른 데이터가 발견되면 실패하도록 되어 있다.
