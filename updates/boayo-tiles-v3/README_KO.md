# BoAYO 내장 자료 빠른 로드·정수 버전·요청 묶음 — tiles-v3

## 범위

`variants/sd4-dma/` 하드웨어와 기존 SD4·DMA 비트스트림을 유지한다. 소프트웨어 기준은 보존된 `updates/boayo-tiles-v2`이며, 이 디렉터리는 분리된 새 소프트웨어 업데이트다. CPU 스케줄러, 실행기, 두 투영코어, BS25, DMA, MIG, HDMI RTL과 레지스터 ABI는 수정하지 않았다. 기존 Linux/BusyBox/SD4/ext4 `/data`를 유지한다. 원본 Python/기존 렌더러는 비교용으로 보존했다.

이번 산출물은 새 SD 이미지와 소스·검증 기록이다. **보드에 업로드하거나 실제 HDMI·속도를 측정하지 않았다.** 로컬 통과와 실보드 확인은 구분한다.

## 실제 처리 순서

1. 전용 예약 DDR를 매핑한다. 16MiB 전체나 4,220개 타일의 Cell Data를 0으로 지우지 않는다.
2. 첫 빈 화면은 팔레트와 무효 디렉터리만 작성하여 표시한다. 반대 버퍼는 즉시 복제하지 않는다.
3. BoAYO가 모은 이벤트에서 이전·새 창 위치, 내용, 모양, 순서, 포인터의 영향을 받는 타일을 결정한다.
4. 타일별 요구 버전과 A/B 버퍼의 저장 버전을 관리한다. 비활성 타일에는 픽셀 작업을 발행하지 않는다.
5. 변경된 타일은 새 장면의 아래 레이어부터 재구성한다. 맨 아래 투영이 전체 타일을 덮으면 사전 Fill을 하지 않는다. 나머지 활성 경계 타일은 필요한 타일만 배경을 준비한다.
6. 명시적인 단색 `fill` 정보가 유효하고 타일 전체를 덮으면 투영 대신 DMA Fill을 사용한다. 복잡한 텍스처는 기존 투영 경로를 사용한다. 기존 마스크 경계 일부는 CPU 워드 단위 수정이 남는다.
7. 변경되지 않은 활성 타일 중 목적지 버퍼가 오래된 것만 최신 버퍼에서 DMA로 복사한다. 동일 버전이 이미 있으면 아무 작업도 하지 않는다. 숨겼던 타일의 저장 데이터도 지우지 않는다. 창·소스 수정 버전·기하·모양·포인터 구성의 정확한 식별 정보가 다시 같아지면 기존 타일을 재사용한다. 해시 충돌이나 픽셀 읽기 비교에 의존하지 않는다.
8. 목적지 버퍼의 메타데이터 중 다른 연속 구간만 기록한다. 모든 필요한 타일의 버전과 작업 완료를 확인한 뒤 전환한다.
9. 드라이버는 마지막으로 전환 완료한 메타데이터와 새 메타데이터를 정확히 비교한다. 동일하고 장면 길이도 같으면 `0x6C=2`, 최초이거나 다른 경우 `0x6C=1`이다. `0x44`와 완료/오류 상태를 함께 확인한다.
10. 전환 직후 반대 버퍼 복사는 없다. 다음 작업에서 필요한 버전만 확보한다. 이벤트가 없으면 투영·복사·로드·버퍼 교체도 없다.

하나의 타일에는 Fill→아래 창 투영→위 창 투영→포인터 같은 순서가 적용될 수 있다. 같은 목적지의 레이어 순서는 지키며 서로 다른 타일 작업은 두 투영코어에 분배한다. 창 이동·삭제 때 단순히 옛 픽셀을 보존하지 않고 영향을 받은 타일을 새 장면 기준으로 재구성한다.

## 형식 및 소유권

- M=32, 타일당 1,024셀·1,024바이트. 디렉터리 4,220개, 무효값 `0xFFFFFFFF`.
- Cell Data는 **4,476워드 뒤**에서 시작한다. 팔레트 256 + 디렉터리 4,220 = 4,476워드다.
- BS25의 기존 정렬 읽기는 4,480워드다. 추가 4워드를 CPU 메타데이터 쓰기나 초기화 대상으로 취급하지 않는다. 기존 하드웨어 정렬 읽기와 비활성 타일 더미 캐시 접근은 그대로다.
- CPU에는 출력 픽셀 사본이 없다. 메타데이터, 타일 버전, 창 상태와 동적 2D 소스만 관리한다. 메타데이터 비교는 17,904바이트 범위이며 전체 장면 DDR 비교가 아니다.
- 활성 버퍼는 쓰지 않는다. 모든 생성·복사 완료와 메모리 배리어 후 전환 요청을 발행한다. 전환 완료 뒤에만 이전 활성 버퍼를 반환한다.
- DMA/투영/전환 오류·타임아웃은 실패 상태를 잠근다. 늦은 작업이 있을 수 있으므로 임의 재시도나 버퍼 재사용을 하지 않는다. 작업 실패 전 정상 화면은 유지하되, 이미 발행한 전환의 타임아웃은 실제 전환 여부가 불확실한 상태로 취급한다. 리셋 전 자동 복구를 완료했다고 주장하지 않는다.

## tiles-v2에서 바뀐 부분

| 항목 | tiles-v2 | tiles-v3 |
|---|---|---|
| 내장 투영 계획 읽기 | 실행 때 본문 CRC와 44개 경계 마스크 전체 검사 | 이미지 제작 때 전체 검증, 실행 때 형식·버전·범위 확인만 |
| 타일 재사용 판정 | 기하·모양·수정 상태를 타일별 JSON 문자열로 직렬화 | 창 ID·배치 버전·타일 내용 버전의 순서 있는 정수 목록 비교 |
| 초기 경계 배경 준비 | 44회 개별 요청 | 44개 항목을 1회 묶음 요청 |
| 초기 경계 합성 | 44회 개별 요청 | 44개 항목을 1회 묶음 요청 |
| 복사·단색·포인터 | 개별 요청 | 순서를 유지한 최대 128개 묶음 |
| 전체 장면 초기화·전환 뒤 즉시 복제 | 없음 | 없음 |

초기 런처의 해당 호출은 88회에서 2회로 줄었다. **DMA 자체의 처리 횟수나 96개 투영 작업 수를 2회로 줄인 것은 아니다.** 각 작업의 완료 대기와 하드웨어 처리 시간은 남는다. 첫 화면이 몇 초 빨라졌는지는 새 이미지의 실보드 측정 전에는 알 수 없다.

JSON 제어 프로토콜·상태 출력·창 설정은 호환성을 위해 유지한다. 없앤 것은 타일마다 반복하던 JSON 내용 식별 문자열이다. 정수 목록은 정확히 비교하며 해시 충돌에 의존하지 않는다. 작은 2D 수정은 영향을 받은 타일의 내용 버전만 바꾼다. 창 이동·모양 변경은 배치 버전을 바꾸고, 가림 순서는 목록 순서에 반영한다. 숨김 뒤 같은 내용의 재등장은 기존 타일을 재사용한다. 이동했다 돌아온 기하는 안전하게 재투영할 수 있다.

신뢰하는 내장 계획은 initramfs의 `/usr/share/boayo/plans`에 설치한 파일이다. `install_plans.py`가 이미지 제작 시 SHA-256, CRC, 키, 모든 디스크립터 범위, 마스크 값과 분류를 확인한다. 외부 `/data/boayo-plans` 및 명시적 `BOAYO_PLAN_DIR` 파일은 여전히 전체 검증한다. 비활성 버퍼 소유권·주소 범위·완료·타임아웃 검사는 제거하지 않았다.

`BO_BATCH`는 기존 ABI3의 추가 선택 기능이며 기존 ioctl과 RTL 레지스터는 그대로다. 드라이버가 사용자 목록을 한 번 복사하고 전체 항목을 검사한 뒤 순서대로 실행한다. 잘못된 마지막 항목도 앞 작업 실행 전에 거부한다. 실행 중 실패하면 앞 작업 일부가 끝났을 수 있으므로 장치를 실패 상태로 잠그고 새 장면을 표시하지 않는다. 새 앱은 새 드라이버가 들어 있는 SD 이미지와 함께 사용한다.

## 기능 범위

기본 런처, Dashboard/Telemetry/Pulse, 이동·회전·크기·모양·가림·삭제·포인터/WASD 기능을 기존 결과와 비교한다. 임의 알파 혼합 하드웨어는 추가하지 않았다. 둥근 모양의 마스크는 투영 후 DMA 연속 구간 및 CPU의 일부 워드 수정으로 합성한다. 장식 창, 가로 시야각 160도 이상, 외부 전체 장면 합성은 기존 지원 제한을 유지한다. `BOAYO_RENDERER=legacy`는 명시적인 비교용 경로이며 기본 경로에서 자동 선택하지 않는다.

## 재현 및 증거

```sh
bash build.sh /var/tmp/oryukdo-boayo-tiles-v3/release
bash validate.sh /var/tmp/oryukdo-boayo-tiles-v3
python3 package.py /var/tmp/oryukdo-boayo-tiles-v3 /mnt/d/temp/gen3bosio/boayo-tiles-v3
```

빌드는 이전 RGBDMA 기반 Linux/OpenSBI/BusyBox 및 기존 RV32 툴체인을 사용하되 새 디렉터리에 소스와 산출물을 만든다. 최종 판정과 해시는 `result.json`, `SHA256SUMS.txt`를 따른다. `evidence/`에는 호스트·ASan/UBSan·실제 드라이버 함수·기존 BS25 RTL·SD RTL·QEMU 및 이미지 일치성 결과를 보관한다. QEMU BOSIO와 RTL DDR은 모형이다. 전체 CPU RTL Linux 콜드 부팅, 새 Vivado 배선, 실보드 HDMI 검증은 이번 범위에 포함하지 않는다.
