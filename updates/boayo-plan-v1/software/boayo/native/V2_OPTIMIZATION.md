# BoAYO C++ v2 구조와 검증 범위

2026-11-09. 보드는 사용자가 나중에 켜기로 했으므로 이번 작업은 PC/WSL에서 수행한다. v1의 Python 기준, C++ 소스 ZIP, 이미지 및 실보드 실패·미완료 기록은 보존한다. RTL·MIG·HDMI IP·BOSIO 드라이버 ABI 및 비트스트림은 변경하지 않는다.

## 고정 기하와 계산

`src/fixed_geometry.inc`는 v1의 20개 면, 4,220개 삼각형 및 기본 카메라를 미리 계산한 읽기 전용 표다. `Geometry`는 표를 참조하므로 생성할 때 삼각함수·타일별 부동소수점 계산·전체 표 복사를 하지 않는다. 기본 자세 외의 카메라는 기존 방식으로 계산한다.

재생성 기준은 `tests/geometry_baseline.hpp`에 보존한 v1 계산식이다. `tests/generate_geometry.cpp`가 16진 부동소수점 리터럴을 출력한다. 호스트와 RV32에서 생성한 표를 바이트 단위로 비교했고, `tests/test_geometry.cpp`는 원래 계산과 표의 모든 double 비트, 기본 및 회전 카메라, 33,760개 투영 기술자를 비교한다. `benchmark_v2.sh`는 보존한 v1 소스와 현재 소스를 동일한 RV32 조건에서 비교한다.

각 창의 축·FOV 계수는 타일 4,220개마다 다시 계산하지 않고 한 번 계산한다. 기술자의 양자화·반올림·정수 투영식은 유지한다. 마스크가 없는 창은 마스크 검사에 필요하지 않은 부동소수점 나눗셈을 생략한다.

## 버퍼 갱신

전체 합성 결과는 합성기가 소유한 장면을 동기적으로 참조한다. 출력 함수가 끝나기 전에 다음 합성을 시작하지 않는다. 업로드 범위는 원본 데이터의 주소와 길이를 참조하고, 팔레트 변환만 256워드의 작은 임시 배열을 사용한다. 전체 장면을 임시 컨테이너에 복제하지 않는다.

부분 갱신은 모든 범위를 먼저 검증한 후 비활성 뱅크에 쓰고, 프레임 전환 완료를 기다린 다음 이전 뱅크에 같은 내용을 반영한다. 성공 후 변경된 범위만 shadow에 복사한다. 한 타일 BPT2 갱신의 shadow 복사는 257워드(1,028바이트)다. 전송·전환·반대 뱅크 반영이 실패하면 출력 상태를 실패로 고정하고 shadow를 성공 상태로 갱신하지 않는다. 실패 주입 시험은 전환 전·전환 시·전환 후 반영 실패를 포함한다.

초기 고정 슬롯 장면에서는 팔레트·전체 디렉터리·유효 타일만 양쪽 뱅크에 쓴다. 디렉터리의 `0xffffffff`는 기존 출력 RTL에서 무효 타일을 뜻한다(`soc/vendor/output/bosio_ddr_scene_cache.v`). 생략한 타일은 접근할 수 없고, 이후 BPT2로 타일을 활성화할 때 256워드 전체를 먼저 쓴다. 두 뱅크를 서로 다른 쓰레기 값으로 채운 시험으로 디렉터리 덮어쓰기와 새 타일 활성화를 검사한다. 일반 전체 장면 업로드는 기존대로 전체 데이터를 전송한다.

## 통신과 화면 계산

```text
UART 클라이언트 / 기존 JSON 클라이언트
                  ↓
통신 스레드 ── 상태 조회: 마지막 완료 스냅샷 + 현재 단계
    │
    └── 명령 큐 → 단일 작업 스레드
                    WM·앱 → 합성 → 투영코어/출력코어 접근
                                    ↓
                              완료 후 상태 게시
```

장치·WM·앱·합성기·장면 버퍼는 작업 스레드 하나가 소유한다. 통신 스레드는 장치 ioctl을 호출하거나 렌더링 버퍼를 읽지 않는다. 상태 게시용 잠금은 작은 상태 객체를 교체할 때만 잡으며, 화면 계산·장치 대기 중에는 잡지 않는다. 상태는 `service.state_is_snapshot=true`이며 `snapshot_age_seconds`로 얼마나 오래된 결과인지 표시한다. 계산 중 상태를 현재 화면이 완성됐다는 증거로 해석하지 않는다.

`service.phase`는 초기화, 장치 열기, 합성기 할당, 초기 장면 합성/전송, 데스크톱 초기화, 명령, 앱 갱신, 합성, 전송, 대기, 실패 등을 표시한다. 초기화가 끝나기 전의 상태는 최소 필드만 포함한다. 명령은 실제 처리한 뒤 응답하며, 동일 연결의 순서를 보장한다. 별도 상태 연결은 다른 연결의 대기 명령에 막히지 않는다. 화면 계산을 중간에 끊고 새 시야를 적용하는 구조는 아니므로 WASD 응답은 진행 중인 한 프레임이 끝날 때까지 기다릴 수 있다.

통신 소켓을 무거운 초기화 전에 연다. `boayo-start`의 성공 문구는 **서비스가 열렸다는 뜻**이다. `BOAYO_NATIVE_READY initial_scene_committed` 역시 초기 장면 반영까지의 표시이며 런처 HDMI 표시 완료와 다르다. `render_error`, `app_error`, `projection`, `output`, `performance`와 실제 화면을 함께 확인한다. 종료 요청은 먼저 수락하고 작업 스레드의 현재 장치 작업이 끝난 후 정리한다. 커널의 장치 호출이 끝없이 멈추는 상황까지 강제 복구하는 기능은 아니다.

시작 보조 프로세스는 fork 후 실행 파일을 재실행하지 않는다. 새 RV32 실행 파일은 정적으로 연결해 동적 C++ 라이브러리 로딩을 없앴다. 제공되는 ELF가 모두 정적 실행 파일임을 검사한 뒤 사용하지 않는 공유 라이브러리를 새 루트에서 제외한다. 외부 프로그램을 추가할 때도 정적 RV32IMA/ILP32로 빌드하거나 필요한 공유 런타임을 별도로 포함해야 한다.

## 검증과 다음 실보드 단계

기존 Python 비교, UI 픽셀, 앱 상태, 두 정수 투영 모델, CPU 대체 합성, 실제 Unix IPC, 가상 터미널 WASD/CRLF 클릭 시험을 유지한다. ASan/UBSan으로 같은 시험을 반복한다. `test_responsive.py`는 Mock 렌더링만 3초 지연시켜 그동안 상태 조회가 응답하는지 검사한다. 이 지연 기능은 실제 장치 모드에서는 활성화되지 않는다.

SD의 실제 커널 내장 initramfs를 추출해 파일·링크·모드·해시를 대조하고, RV32 ISA와 정적 의존성을 검사한다. QEMU는 SD에서 추출한 정확한 OpenSBI·커널·DTB를 사용해 BusyBox 쉘·상위 RAM 16페이지·BoAYO Mock·입력을 확인한다. 이것은 SD SPI부터 부팅하는 ORYUKDO RTL 검증이나 실제 FPGA/MIG/HDMI 검증이 아니다. 중단한 전체 CPU RTL 시험은 재시작하지 않는다.

실행 결과와 이미지 해시는 최종 산출물의 `RESULTS.md`, `reports/`, `release.json`에 기록한다. PC/QEMU의 시간 감소율을 실제 보드의 부팅 시간·프레임률로 환산하지 않는다.

보드를 나중에 켤 때 새 `ORYUKDO-KFB-BoAYO-native-v2-raw.img`를 SD에 기록·검증하고 기존 비트스트림을 사용한다. 쉘에서 `boayo-start`, `boayo-status`, `boayo-keys`로 확인한다. 런처는 시작 시 자동으로 열리며 다시 열려면 `boayo-launcher`를 입력한다. 현재 전용 런처 키는 없으므로 키 조작 중이면 Q로 쉘에 나온 뒤 실행한다. Bash·Vim·SD 영구 파일시스템은 추가하지 않는다.
