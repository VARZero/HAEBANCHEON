# 키보드와 외부 리모컨 입력

v16b부터 Home 키는 홈런처로 간다. 열려 있는 홈 화면을 앞으로 가져오고, 없으면 홈런처를 실행한다. 대시보드는 홈 화면의 Dashboard 아이콘으로 실행한다. 부팅 시 홈런처 자동 실행과 앱 등록 파일은 그대로 사용한다. v16c부터 홈 화면 바깥의 닫기·이동·크기 조절 버튼을 표시하지 않으며 키보드에서도 숨긴 닫기로 이동하지 않는다. 앱 내용의 Home·Reload 제목 띠와 아이콘은 유지한다.

v16a는 기존 FPGA 비트스트림을 그대로 쓰고 리눅스 커널과 보아요 소프트웨어를 바꾼 버전이다. 2026-11-27 실제 보드에 적용해 UART 콘솔에서 실행한 입력 앱과 HDMI 화면을 함께 검사했다. 실제 RV32 바이너리의 부팅·TTY 입력은 QEMU에서도 검사했고, SPI 전송은 모의 장치로 검사했다. 실물 ESP32 통신은 아직 검사하지 않았다.

v16a에서는 닫기 버튼의 키보드 선택 상태를 마스크 캐시에 반영했다. v16은 내부 포커스가 닫기로 옮겨져도 이미 만든 흰색 마스크가 재사용되어 선택색이 보이지 않았다. 기존의 누름 상태 마스크를 재사용하도록 수정했으며, 캐시가 채워진 뒤 선택·해제를 반복하는 검사도 추가했다.

## TTY에서 실행

UART 터미널에서 다음 앱을 실행한다. 앱이 실행된 동안 해당 터미널의 입력을 보아요에 전달한다.

```sh
boayo-input
```

기본 입력은 표준입력이다. 터미널의 문자 변환과 화면 에코를 끄고 키를 읽으며, **Ctrl+C로 종료하면 기존 TTY 설정을 복구한다.** SIGTERM·SIGHUP으로 정상 종료할 때도 복구한다. 별도의 UART는 다음처럼 지정한다.

```sh
boayo-input --tty /dev/ttyS0
```

별도 UART는 115200 baud, 8N1로 설정한다. 기존 콘솔 `hvc0`는 유지한다. 기본 실행은 SPI나 다른 TTY를 자동으로 열지 않는다. 백그라운드 입력이 필요하면 장치를 명시한다.

```sh
boayo-input --spi /dev/spidev0.0 >/tmp/boayo-input.log 2>&1 &
boayo-input --auto --spi /dev/spidev0.0 >/tmp/boayo-input.log 2>&1 &
boayo-input --event /dev/input/event0
```

`--auto`는 리눅스의 `/dev/input/event*`를 주기적으로 찾아 연다. 장치가 사라지면 다시 연결을 기다린다. 기존 FPGA에는 USB 호스트가 없으므로 이 옵션을 켠다고 일반 USB 키보드를 보드에 바로 연결할 수 있는 것은 아니다. ESP32가 키보드를 받아 SPI로 전달하거나, UART로 키를 보내는 외부 장치가 필요하다. ESP32의 키보드 수신 펌웨어는 후속 작업이다.

입력 앱은 자동 실행하지 않는다. WM은 기존처럼 홈런처로 시작하고, 입력이 필요한 TTY나 SPI에서 `boayo-input`을 실행하면 된다. 하나의 TTY나 SPI 장치는 입력 앱 하나에서 사용한다.

## 현재 키 동작

| 키 | 동작 |
|---|---|
| Home | 홈런처를 열고 포커스한다. 이미 열려 있으면 같은 홈 화면을 앞으로 올린다. 대시보드는 홈의 앱 아이콘으로 실행한다. |
| 방향키 | 활성 창의 선택·입력 가능한 컴포넌트 중 해당 방향의 가까운 항목으로 이동한다. |
| Enter | 선택된 컴포넌트의 중앙을 클릭한 것과 같은 이벤트를 보낸다. |
| 위쪽에 더 이상 항목이 없는 상태에서 ↑ | 창 닫기로 이동한다. 닫기 아이콘의 색이 바뀐다. |
| 닫기에서 ↓ | 창 내용의 첫 항목으로 돌아온다. |

첫 포커스는 활성화된 항목을 위에서 아래, 같은 높이에서는 왼쪽에서 오른쪽으로 정렬해 고른다. 일반 방향 이동은 화면 가장자리에서 반대편으로 순환하지 않는다. 컴포넌트에는 밝고 어두운 두 줄로 선택 표시를 넣어 배경색과 구분한다. 선택이 바뀐 부분만 기존 변경 영역 전송 경로로 갱신한다.

에디터의 저장·본문, 설정의 색·포인터·적용, 대시보드 새로고침, 홈런처 아이콘·페이지·다시 읽기, 제어센터의 정면 복귀·전원 종료, 터미널의 조작 버튼·본문에 포커스 정보를 추가했다. 창 이동·크기 조절은 기존 포인터 동작을 유지한다. 현재 입력 앱이 전달하는 키는 Home·방향키 네 개·Enter다. 일반 문자 입력이나 입력창 내부 커서 이동은 이번 키 탐색 기능에 포함하지 않는다.

## UART에서 보내는 내용

일반 터미널의 ANSI 방향키 `ESC [ A/B/C/D`, Home `ESC [ H`, `ESC O H`, `ESC [ 1 ~`, `ESC [ 7 ~`를 받는다. Enter의 CR·LF·CRLF를 처리하며 CRLF를 두 번 클릭으로 세지 않는다. 여러 번에 나뉘어 도착한 이스케이프 시퀀스도 이어서 읽는다.

외부 리모컨은 다음 텍스트 형식도 사용할 수 있다.

```text
KEY Home
KEY ArrowRight
KEY ArrowDown
KEY Enter
```

터미널 프로그램이 Home·방향키를 로컬 단축키로 가로채지 않고 UART로 전송하도록 설정해야 한다. 데몬 연결만 확인하려면 다음 명령으로 키 하나를 보낼 수 있다.

```sh
boayo-input --key Home
```

## ESP32와 SPI

SoC가 마스터이고 ESP32가 슬레이브다. 설정은 **SPI mode 1, MSB first, 8비트, 1MHz**다. GPIO 인터럽트 없이 입력 앱이 약 20ms 간격을 목표로 확인한다. 이 값은 폴링 설정이며 실제 화면 반응 시간이 아니다. 시스템 부하와 전송 시간에 따라 간격이 길어질 수 있다.

ESP32의 DMA 사용 조건을 고려해 mode 1과 4바이트 배수인 20바이트 프레임을 사용한다. ESP32 쪽 DMA 버퍼는 해당 칩의 정렬·메모리 조건에 맞게 준비해야 한다. [Espressif SPI 슬레이브 문서](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/peripherals/spi_slave.html)를 기준으로 잡았다.

한 번 CS를 내린 동안 20바이트를 전송한다. 다중 바이트 정수는 리틀 엔디언이다. 각 바이트 안의 비트 순서는 MSB first다.

| 오프셋 | 길이 | ESP32 → SoC |
|---|---:|---|
| 0 | 4 | ASCII `KBD1` |
| 4 | 4 | 부팅 세션 번호. 부팅할 때마다 새 0이 아닌 값 |
| 8 | 4 | 이벤트 순번. 1부터 증가하며 0은 건너뜀 |
| 12 | 1 | 0=없음, 1=Home, 2=←, 3=→, 4=↑, 5=↓, 6=Enter |
| 13 | 1 | 0=놓음, 1=누름, 2=반복 |
| 14 | 2 | 예약, 0 |
| 16 | 4 | 앞 16바이트의 CRC-32/IEEE |

이벤트가 없을 때는 키·상태·순번을 0으로 보낸다. 세션 번호와 CRC는 유효해야 한다. SoC가 동시에 보내는 프레임은 `KACK`, 세션 번호, 수신 처리한 순번, 예약 4바이트 0, CRC 순서다.

ESP32는 큐의 맨 앞 이벤트를 반복 전송하고, **세션과 순번이 맞는 유효 ACK를 받은 뒤에만** 제거한다. ACK는 데몬이 키 요청을 처리했다는 뜻이다. 포커스된 창이 아직 준비되지 않아 거절한 경우도 로그를 남기고 소비하며, 화면 공개 완료를 뜻하지는 않는다. 데몬 연결이 끊어지면 입력 앱이 재시도한다. 같은 세션·순번은 데몬이 중복 실행하지 않는다. 중복 기록은 최근 소스 32개를 메모리에 유지하며, 데몬 재시작을 넘는 영구 기록은 아니다.

방향키 반복은 탐색에 사용한다. Home·Enter 반복과 키 놓임은 ACK만 보내며 다시 실행하지 않는다. 입력 앱의 대기열은 512개로 제한한다. SPI 이벤트를 대기열에 넣지 못하면 ACK하지 않아 ESP32가 보관한다. TTY·evdev 대기열이 가득 차면 새 입력을 받지 못했다는 로그를 남긴다.

[공통 프레임 코드](src/key_transport.hpp)와 [ESP32 쪽 큐 참고 구현](src/esp32_key_queue.hpp)을 제공한다. 큐 참고 구현은 SPI 슬레이브 작업 하나에서 사용하는 로직이며, ESP-IDF 드라이버나 키보드 수신부까지 포함한 펌웨어는 아니다. 다른 작업에서 키를 만들면 RTOS 큐 등으로 전달해야 한다. ACK가 늦어 이미 준비한 응답에 이전 이벤트가 한 번 더 실려도 같은 이벤트를 다시 실행하지 않는다.

기존 FPGA 핀은 SCK=W15, MOSI=W16, MISO=AB16, CS_n=AB17이다. ESP32의 대응 핀은 사용할 보드에 맞춰 정한다.

## 리눅스 연결

| 장치 | 주소 | 드라이버 |
|---|---|---|
| 범용 UART | `0x10005000` | 8250 고정 타입, 인터럽트 없는 폴링, 8N1. 예상 장치 `/dev/ttyS0` |
| SPI 마스터 | `0x10006000` | 모드 0–3, 8비트, CS 하나. ESP32 장치 `/dev/spidev0.0` |
| I²C 마스터 | `0x10007000` | 7비트 주소, 반복 START·NACK·STOP·오류 처리. 예상 장치 `/dev/i2c-0` |

보드 장치 트리와 드라이버를 추가하고 evdev·uinput·SPI·I²C를 커널에 포함했다. GPIO나 인터럽트가 있는 것처럼 가정하지 않았다. 기존 SBI 콘솔을 다른 8250 드라이버가 동시에 열지 않도록 일반 OF 8250 자동 연결은 껐다. `BO_PUBLISH_COPY`와 기존 WM 최적화는 유지했다.

실제 보드에서 `/dev/ttyS0`, `/dev/spidev0.0`, `/dev/i2c-0` 등록과 드라이버 연결을 확인했다. 이번 키 검사는 기존 SBI 콘솔 TTY에서 진행했다. 범용 UART 핀의 송수신과 외부 SPI·I²C 신호는 별도 장치를 연결해 확인해야 한다. QEMU 검사는 이 MMIO 장치를 흉내 내지 않는다.

## 앱에서 포커스 등록

앱 소켓에서 `set_focusables`에 `window_id`와 `targets` 배열을 보낸다. 각 항목에는 `id`, `x`, `y`, `w`, `h`, 선택적인 `enabled`가 들어간다. 좌표는 앱 화면의 픽셀 좌표이며 창당 최대 128개다. ID는 중복할 수 없고 `$`로 시작하는 이름은 WM이 사용한다. 다른 앱 창의 정보를 바꿀 수 없다.

앱에는 `focus` 이벤트의 `target`이 전달된다. Enter는 기존 `click` 이벤트와 좌표를 전달하므로 포인터 클릭 코드를 재사용할 수 있다. `app_ui::Canvas::target()`과 `app_ui::Window`가 등록·선택 표시를 처리한다. 입력 도구는 제어 소켓의 `input_nav`를 사용하고, `navigation_status`로 선택된 창과 항목을 확인한다. 기존 `input_key`·`input_text` 앱 입력 API는 유지한다.

## 2026-11-27 v16c 홈 창 버튼 숨김과 실제 터미널 검사

실제 HDMI에서 홈 화면 바깥의 닫기·이동·크기 조절 아이콘이 사라진 것을 확인했다. 세 아이콘의 기존 위치에서 흰색 픽셀 수가 각각 237·379·150개에서 모두 0개로 바뀌었다. 홈의 조작 버튼 목록은 비어 있고, 첫 항목에서 ↑를 보내도 포커스가 Reload에 머문다. 일반 터미널 창에는 세 버튼이 표시된다. 터미널에서 홈으로 돌아온 뒤에도 홈의 바깥 버튼은 나타나지 않았다.

그래픽 터미널에 기존 `input_text` 앱 API로 명령을 전달했다. PTY 셸이 만든 파일의 내용 `PTY_REAL`, 실제 TTY `/dev/pts/0`, 커널 `6.12.0-haebancheon-keyboard`를 별도 UART 콘솔에서 읽어 확인했다. 창에 셸 출력이 표시된 화면도 저장했다. 이는 일반 문자 입력을 `boayo-input`에 추가한 결과가 아니다. 현재 UART·SPI 키 탐색 경로는 여전히 Home·방향키·Enter만 전달한다.

UART Home 전송 완료부터 캡처의 홈 제목이 기준 화면과 일치하기까지 1.31초가 걸렸다. 1회 관측이며 USB 캡처 지연을 포함한다. 이전 검사는 대시보드에서 출발했고 이번 검사는 터미널에서 출발했으므로 속도 개선율로 비교하지 않는다. [실보드 검사 결과](results/home-caption-board.json)를 참고한다. WM 실행 파일을 SD와 RAM에 교체해 검사했으며, 완성된 새 SD 이미지는 실제 RV32 QEMU에서 별도로 부팅 검사했다.

## 2026-11-27 v16b 홈 화면 전환 검사

실제 보드에서 홈의 Dashboard 아이콘을 방향키·Enter로 실행하고, 콘텐츠가 표시된 대시보드를 앞으로 가져온 뒤 UART Home 키로 홈 화면에 복귀하는 것을 확인했다. 기존 홈런처 창 ID 1을 재사용했고, 반복 Home 요청 뒤에도 홈런처 1개·대시보드 1개가 유지됐다. PC 검사에서는 홈런처가 없는 상태의 실행과 아이콘을 통한 대시보드 실행도 확인했다. 새 SD 이미지의 실제 RV32 부팅 검사도 통과했다.

대시보드에서 Home을 보낸 뒤 HDMI 캡처의 제목 영역이 미리 저장한 홈 화면과 일치하기까지 **2.32초**가 걸렸다. 1회 관측이며 입력·앱·WM·화면 게시·USB 캡처 지연을 모두 포함한다. 이전 v16a의 새 대시보드 실행과는 작업이 달라 속도 비교로 사용하지 않는다.

이번 보드는 WM 실행 파일만 교체하고 서비스를 다시 시작했다. 완성된 v16b SD 이미지 자체를 실보드에서 새로 부팅한 것은 아니다. [홈 화면 전환 결과](results/home-launcher-board.json)에 실제 UART·HDMI 관측과 검사 범위를 기록했다.

## 2026-11-27 v16a 실보드 검사

아래는 Home이 대시보드에 연결돼 있던 v16a의 기록이다. v16b 홈런처 동작의 측정값으로 사용하지 않는다.

Linux `6.12.0-haebancheon-keyboard`에서 `boayo-input`을 콘솔의 전경 앱으로 실행했다. PC에서 COM4로 실제 ANSI 키를 보내고 USB HDMI 캡처를 관찰했다. Home으로 대시보드 표시, 방향키로 닫기·설정 항목 선택, Enter로 창 닫기·색상 선택을 확인했다. 닫기 버튼의 선택색은 캐시 수정 후 실제 화면에서도 바뀌었다. FPGA는 변경하지 않았다.

다음 시간은 **PC에서 UART 쓰기를 마친 시점부터 실제 HDMI 캡처의 판정 영역이 바뀔 때까지**다. UART·앱·WM·게시·캡처 버퍼와 샘플링 지연이 모두 포함된다. 입력 수락 시간이나 보드 내부 렌더링 시간만을 뜻하지 않는다.

| 동작 | 관측 시간 | 횟수·판정 |
|---|---:|---|
| 대시보드에서 ↑로 닫기 선택 | 2.74초 | 마지막 확인 1회, 닫기 아이콘 영역 |
| Enter로 대시보드 닫기 | 3.36초 | 마지막 확인 1회, 고정된 제목 영역의 교체 |
| 설정창의 방향키 선택 이동 | 중앙값 14.39초, 13.52–15.95초 | 5회, 설정창을 표시한 상태 |
| 설정창 색상 항목 Enter 선택 | 16.01초 | 1회 |
| Home으로 새 대시보드 열기 | 첫 변화 3.59초, 콘텐츠 11.45초 | 초기 검사 1회 |

빠른 입력 반응 목표를 달성한 결과가 아니다. 설정 앱의 nice 값을 +10에서 0으로 바꾼 별도 탐색에서는 좌우 이동 3회가 8.46–9.37초였다. 처리 우선순위의 영향은 보이지만 표본과 동작이 완전히 같지 않아 확정적인 개선율로 쓰지 않는다. 비교 후 +10으로 복구했으며 SD의 기본 우선순위도 바꾸지 않았다. Home이 실행한 대시보드는 WM의 우선순위를 물려받으므로 두 앱의 시간 차이를 렌더링 작업량만으로 설명할 수 없다.

닫은 직후 Home을 눌렀을 때 30초 동안 새 화면이 나오지 않은 경우도 1회 있었다. 이후 콘솔에서 Home 요청을 다시 보내자 대시보드가 표시됐다. 앞선 검사에서 제목 외 영역의 변화만으로 닫기를 판정한 기록은 완료 지연으로 쓰지 않았다. 원래 앱의 종료 대기와 TTY 입력 전달 중 어느 쪽인지 아직 분리하지 못했으므로 빠른 닫기·재실행을 보장하지 않는다.

[실보드 결과](results/keyboard-board.json)는 위 관측과 제한을 기록한다. `keyboard-validation.json`과 `keyboard-boot.json`은 별도의 PC·QEMU 검사 결과이며 외부 SPI·I²C 통신 통과를 뜻하지 않는다.

## 콘솔과 HDMI 실시간 보기

PC의 실제 콘솔·HDMI 중계는 다음처럼 실행한다. 캡처 장치 이름은 `USB3.0 Video`, UART는 COM4로 지정돼 있다. 장치가 달라지면 도구의 설정을 맞춰야 한다. Python의 pyserial·OpenCV·NumPy와 FFmpeg가 필요하다.

```powershell
python updates/triangle-wm/tools/board_monitor.py --output updates/triangle-wm/evidence/keyboard-board-20261127/live
```

`http://127.0.0.1:8770/`에서 HDMI와 콘솔을 함께 본다. ‘키 입력 시작’을 누르면 현재 TTY에서 입력 앱이 실행되고 Home·방향키·Enter 버튼을 사용할 수 있다. ‘Ctrl+C’를 누르면 콘솔로 돌아온다. 같은 UART를 다른 도구가 동시에 열면 안 된다. 이 중계는 PC에서 수동 실행하는 개발 도구이며 SD의 자동 실행 항목이 아니다.
