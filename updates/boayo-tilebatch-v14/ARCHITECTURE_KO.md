# v14의 CPU·DMA·투영코어 분담

## 한 번의 앱 부분 갱신

1. CPU가 입력과 창 위치·크기·앞뒤 순서를 갱신한다. 앱은 기존 2D 이미지에서 달라진 영역과 사용할 에셋을 표시한다. 에셋이 없는 동적 요소는 CPU가 만든다.
2. CPU는 변경 영역을 32×32 구획에서 정리한다. 2×2픽셀이 구획 경계를 넘어도 변경량은 4픽셀로 유지한다. 떨어진 사각형을 하나의 큰 경계 상자로 합치지 않는다. 같은 행 범위 또는 열 범위의 연속 사각형만 빈틈 없이 합친다.
3. 창의 2D 이미지와 수정 버전을 기존 4MiB DDR 텍스처 영역에서 재사용한다. 변경이 없으면 전송하지 않는다. 이전 프레임을 건너뛴 경우에는 아직 반영하지 못한 변경 영역을 누적한다.
4. 작은 불변 에셋이 DDR에 있으면 DMA가 필요한 부분을 창 이미지로 복사한다. 없으면 기존 사용자 메모리 업로드 API로 올린다. 여러 복사 명령을 순서대로 묶어 CPU와 드라이버 사이의 요청 횟수를 줄인다. SD에서 처음 자료를 읽는 기존 경로는 별도이며 이 캐시는 DDR 상주 이후의 재사용이다.
5. 복사가 완료된 뒤 투영코어가 변경된 2D 영역에 영향을 받는 구면 타일을 갱신한다. 투영 요청의 계수와 가림 정보를 CPU가 준비하는 기존 구조는 유지한다.
6. 경계가 걸친 구면 타일은 기존 마스크·합성 경로로 처리한다. 출력코어에 완성된 타일 주소와 메타데이터를 전달하고 장면을 전환한다. 수정되지 않은 타일은 재사용한다.

## 경계 합성이 남는 이유

경계 합성은 한 구면 타일에 배경과 창, 또는 앞뒤 창의 일부가 함께 들어갈 때 보이는 픽셀을 조합하는 처리다. 둥근 모서리만을 뜻하지 않는다. 사각형 창도 타일 경계를 가로지르거나 겹칠 수 있다.

이번 변경은 앱 본문 외곽의 곡률을 없애고 버튼은 유지한다. CPU의 투영계수 계산이나 경계 마스크 생성 전체를 하드웨어로 옮기지 않는다. 투영코어 동시 실행과 완료 대기 방식도 바꾸지 않는다.

## 캐시 공간과 수명

- 창 이미지와 에셋은 동일한 텍스처 할당기를 사용한다. 창 공간을 확보할 때 캐시 에셋부터 반환하므로 256KiB를 고정 예약해 최대 창 크기를 줄이지 않는다.
- 에셋 하나는 최대 16,384워드, 캐시 합계는 `min(65,536워드, 전체 용량/8)`다. 기본 구성은 각각 64KiB·256KiB다.
- 소스의 공유 참조를 보관해 주소가 다른 에셋에 재사용되는 문제를 막는다. 가변 창 이미지나 합성 레시피 자체를 불변 에셋으로 저장하지 않는다.
- 에셋을 반환하거나 임시 업로드 경로로 전환하기 전에 대기 중인 복사 묶음을 완료한다. 캐시 영역을 아직 참조하는 DMA가 남아 있는 상태로 해당 주소를 재사용하지 않는다.
- 공간이 없으면 기존 업로드 경로를 사용한다. 에셋을 넣기 위해 살아 있는 창을 강제로 퇴출하지 않는다.
- 복사·업로드 실패 시 대기 명령을 버리고 대상 창 슬롯을 무효화한다. 다음 성공 갱신 전에 부분적으로 완성된 이미지를 정상 버전으로 재사용하지 않는다.
- 최대 128개 복사 명령을 묶는다. 인접 명령의 소스·목적지 주소가 모두 연속일 때만 한 명령으로 합친다.

관련 구현은 `software/boayo/native/src/dirty_regions.hpp`, `texture_pool.hpp`, `apps.cpp`, `wm.cpp`다. 기존 드라이버의 동기 완료 계약을 사용하며 캐시/DMA 일관성을 위한 새로운 하드웨어 규칙은 도입하지 않았다.

## 성능 해석

글자처럼 작은 자료를 자주 반복하면 업로드와 요청 수를 줄일 수 있다. 반대로 계속 새로운 그림을 쓰거나 캐시가 부족하면 캐시 적중이 낮고 관리·복사 비용이 남는다. 32×32 구획도 CPU에서 관리하므로 비용이 0은 아니다. 실보드에서는 앱 계산, 영역 정리, 업로드, DMA 복사, 투영 준비, 투영 실행, 경계 합성, 출력 전환을 구분해서 비교해야 한다.
