# HAEBANCHEON — BoAYO 변경 영역 갱신 v9

창의 2D 이미지를 DDR에 보관하고, 변경된 사각형만 갱신한 뒤 그 영향을 받는 타일을 다시 투영한다. 기존 `boayo-view-v8` 소프트웨어를 별도로 보존했다. RTL·비트스트림·Linux 드라이버·UAPI는 변경하지 않았다.

## 화면을 갱신하는 순서

1. 첫 사용 때 창의 2D 이미지를 기존 4MiB 텍스처 영역에 배치한다. 창별 주소를 유지한다.
2. 에셋 기반 이미지는 이전/새 기본 이미지와 조각 목록을 비교한다. 바뀐 조각의 이전 위치와 새 위치를 변경 영역으로 기록한다. 변경되지 않은 동일 조합은 새 콘텐츠 버전도 만들지 않는다.
3. 변경 영역에 기본 배경과 겹치는 조각을 순서대로 복원한다. 이동·삭제된 조각의 잔상을 남기지 않는다.
4. 연속된 작은 조각은 한 번 업로드한 뒤 DMA 행 복사를 묶어서 창의 DDR 이미지에 적용한다. 긴 간격으로 흩어진 원본은 필요한 행만 직접 업로드한다.
5. 변경 사각형과 교차하는 투영 타일만 무효화한다. 창 위치·크기·가림 순서가 바뀌면 기존 기하/가림 처리에 따라 필요한 타일을 갱신한다.
6. 두 투영코어 완료 후 기존 출력 버퍼 전환 경로로 표시한다. 이미 완성된 타일은 기존 DDR 타일 재사용/DMA 복사 경로를 유지한다.

빈 타일은 기존 비활성 메타데이터로 처리한다. 장면 버퍼 전체를 0으로 채우지 않는다. 일부 경계 타일의 합성을 위한 타일 단위 초기화는 필요할 때 유지한다.

## 에셋이 없는 CPU 그리기

CPU가 만든 이미지를 받는 기존 `publish()`도 유지했다. 전체 이미지를 넘기면 기존 이미지와 비교해 변경 사각형만 복사·전송한다. **이 경로는 애플리케이션의 전체 이미지 생성 및 비교 비용까지 없애지는 않는다.**

변경 위치를 이미 아는 CPU 위젯은 `publish_region(wm, id, part, x, y)`를 사용한다. `part`에 필요한 작은 2D 조각만 그리면 나머지 픽셀은 보존된다. 에셋 기반 창을 처음 CPU 수정 방식으로 전환할 때는 CPU 쪽 원본을 한 번 펼칠 수 있다.

Dashboard·Telemetry·런처의 기존 에셋 조합은 자동으로 변경 영역 비교를 사용한다. 애플리케이션이 전체 픽셀을 다시 만들지 않는 경로다.

## 메모리·완료 관리

- 기존 4MiB 텍스처 영역 안에서 첫 빈 구간을 할당한다. 용량/연속 공간이 부족하면 가장 오래 사용하지 않은 창의 텍스처를 버리고 필요할 때 다시 적재한다. 모든 창을 1GiB DDR에 무제한 보관하는 구현은 아니다.
- 투영 디스크립터의 기존 원본 오프셋 필드에 창별 시작 주소를 더한다. 드라이버의 기존 범위 검사와 두 코어의 동기 완료 응답을 사용한다.
- 작은 조각의 DMA 행 복사는 완료를 기다린 후 투영을 시작한다. 경계 타일 투영용 scratch와 동시에 사용하지 않는다.
- 가려진 동안 누적된 수정도 다음 사용까지 보관한다. 창 종료 시 슬롯을 반환한다.
- 전송 실패 시 해당 텍스처 슬롯을 무효화하고 출력 실패를 기록한다. 일부만 수정된 이미지를 정상 완료된 것으로 재사용하지 않는다.
- 기존 일반 장면 합성 주기 제한과 v8 연속 시점 미리보기 동작은 유지한다. 이번 변경이 일반 창 갱신을 10/20fps로 올리는 것은 아니다.

QEMU 부팅 시험은 SD에서 추출한 OpenSBI·커널·DT를 적재한다. FPGA SD 컨트롤러 및 BOSIO/HDMI 하드웨어를 거치는 실보드 콜드 부팅 시험은 아니다.

64×64 원본의 8×8 에셋 조각 수정 시험에서는 16,384바이트 전체 전송 대신 256바이트를 전송했다. Dashboard·Telemetry의 첫 장면 이후 12회 갱신에서는 직접 이미지 업로드가 **6,566,400 → 460,800바이트(92.98% 감소)**였다. 출력 버퍼 전환, 타일 복사, 디스크립터 등 모든 DDR 트래픽을 합한 수치는 아니다. 실행 시간이 같은 비율로 줄었다는 의미도 아니다.

첫 이미지 적재 비용은 남는다. 주된 효과는 첫 화면 이후의 내용 변경과 여러 창 재사용에 있다.

기존 사전 계산 계획 버전 `c830e2bae43593f8c188620447b4ce808ce4894a826a073b44f12b949ad54b7e`를 유지한다. 기하 계산·디스크립터 형식을 바꾸지 않았고, 기존 689개 에셋과 37개 계획을 그대로 사용한다.

## 빌드 및 배포

WSL의 기존 L1-16K/DMA3 Linux 빌드와 motion-v7 배포 루트가 필요하다. `build_image.sh`는 출력 경로에 별도 루트를 복사해 애플리케이션을 교체하고 initramfs를 포함한 커널/SD 이미지를 만든다. 기존 Linux 드라이버 소스나 보드 실행을 수정하지 않는다.

```sh
bash software/boayo/native/build.sh /var/tmp/haebancheon-dirty-v9/host3 host
bash software/boayo/native/build.sh /var/tmp/haebancheon-dirty-v9/sanitize sanitize
bash software/boayo/native/build.sh /var/tmp/haebancheon-dirty-v9/rv32-final rv32
bash build_image.sh /var/tmp/haebancheon-dirty-v9
```

이미지: `D:\temp\haebancheon-dirty-v9\HAEBANCHEON-KFB-BoAYO-dirty-v9.img`

사용 비트스트림: 기존 `HAEBANCHEON-KFB-L1-16K-DMA3-v1.bit`. SPI 전용 또는 캐시/DMA 구성이 다른 비트스트림과 혼용하지 않는다.

보드에 이미지를 기록할 때 `/data` 내용도 교체되므로 보존할 파일은 먼저 백업한다. 이번 작업에서 물리 SD 기록·보드 재시작·UART/HDMI 실측은 하지 않았다. 기존 글자·테두리 표시 문제도 이번 수정으로 해결했다고 판단하지 않는다.

`evidence/`에 빌드 매니페스트와 검사 결과를 보관한다. 배포 이미지 SHA-256 및 QEMU 검사 결과는 해당 결과 파일을 기준으로 확인한다.

## 후속 실보드 확인 — 2026-11-14

위의 실보드 미검증 표기는 이미지 생성 시점의 상태다. 이후 사용자가 기록한 SD로 기존 비트스트림을 올려 dirty-v9 부팅과 Telemetry 갱신을 확인했다. 같은 보드에서 RAM에 복원한 v8과 비교한 결과, 합성 중앙값 4.87→2.41초, 전체 갱신 간격 약 9.2→5.4초, 직접 이미지 업로드 547,200→38,400바이트/회였다. DMA·앱·렌더링 오류는 없었고 최종 실행은 v9로 복귀했다.

처음에는 HDMI 캡처가 검었으나, 23:19 KST에 사용자 케이블 재연결 후 중단된 PC 캡처를 다시 열어 Telemetry 화면과 막대 갱신을 확인했다. 보드 실행은 유지했다. 기존 글자/테두리의 거친 표현은 남아 있다. 작은 표본의 측정 조건, 실제 HDMI 캡처와 도구 재시도 내역은 [실보드 보고서](evidence/board-20261114/README_KO.md) 및 `performance-comparison.json`에 기록했다.
